M10 scope

Implemented in M10

  • Transparent write forwarding
    Any node accepts write requests (POST/PUT/PATCH/DELETE); non-leader nodes proxy the request to the current Raft leader and return the result transparently to the caller.
  • X-Served-By response header
    All API responses include the NodeID of the node that processed the request.
  • X-Raft-Commit-Index response header
    All API responses include the decimal Raft commit index of the serving node at serve time.
  • WriteForwardMiddleware
    Wired in the router after requireWrite, before route handlers. Handler-level 307 leader-redirect responses removed.

Not implemented in M10

  • Per-namespace write sharding (telemetry vs config namespaces routed to different leaders)
  • CRDT state types (conflict-free replicated data types for last-write-wins semantics)
  • Client-side retry logic on 503 during leader election

Limitations

  • Assumes cluster RTT <= 50 ms between nodes; higher latency degrades forwarded write latency
  • Leader unavailability returns 503 immediately with no internal retry
  • In-flight write requests during a leader election may return 503; callers must retry

Retrospective note

M10 — Active-Active Cluster was the first milestone to tackle the core scaling concern: eliminating the requirement for operators to pin writes to the Raft leader. The WriteForwardMiddleware approach proved clean — one middleware, no handler changes. The two live-cluster tests (FS-AaPerNodeTelemetryIsLocal, FS-AaDistributedWritesConvergeOnAllNodes) were intentionally left as t.Skip since full multi-node convergence validation requires a real deployment; those FSIDs were validated manually on the Proxmox cluster during demo. The X-Served-By / X-Raft-Commit-Index headers became a foundation for observability in subsequent milestones.
