Issues found during real-env testing

Issue Severity Root cause Fix
DoH URL stored in upstream_resolvers breaks forwarding Medium normaliseUpstream() appends :53 to HTTPS URLs; forwarder uses raw UDP/TCP DNS, not DoH Use 1.1.1.1:53 / 8.8.8.8:53 in settings. Documentation should clarify that plain DNS addresses are required.
EDNS0 client IP injection requires SKOED_TEST_MODE=1 By design Security guard: spoofing is disabled in production Not a bug. Production use relies on actual client source IPs. SKOED_TEST_MODE=1 is test-only.
DNS SERVFAIL after node restart (stale DoH upstreams) Resolved Settings configured with DoH URLs; after restart node tried to forward to https://....:53 Fixed by setting plain DNS upstreams via API on the leader.

DNS mode comparison: forwarding vs recursive

After the forwarding tests, the cluster was switched to recursive mode via PATCH /api/v1/settings on the leader (Raft-replicated to all nodes). In recursive mode skoed resolves from root hints — no upstream resolver needed. Blocking and dynamic-client filtering continue to work identically.

Recursive mode is ~2.4× slower at peak because uncached queries require a full root-→TLD-→authoritative traversal (3–5 round trips). Once the cache warms, subsequent hits cost near-zero.

Lost queries: 62 / 60,201 (0.10%) in recursive vs 0 / 146,059 (0%) in forwarding. Timeouts occur during the initial root traversal under high concurrency.

Mode trade-off summary

Forwarding
Delegates to upstream resolvers (1.1.1.1, 8.8.8.8). Fast because resolvers pre-cache the global DNS tree. ✓ Lower latency   ✓ Higher peak QPS   ✗ Upstream dependency
Recursive
Resolves from IANA root hints. Self-contained, no upstream needed. ✓ No upstream dependency   ✓ Privacy (no resolver sees all queries)   ✗ Higher cold latency   ✗ Needs Internet reach to root servers
Blocking and dynamic-client filtering work identically in both modes. M14 behavior is mode-agnostic.
